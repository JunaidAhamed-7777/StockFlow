# Frontend capabilities and backend follow-up

The production frontend uses the existing StockFlow API. No changes to `server/`, the Prisma schema, authentication behavior, or database structure were made as part of the frontend improvements. The following limits need backend work before an internet-facing production launch.

## Security issues requiring server fixes

- **Public registration accepts `ADMIN`.** `server/src/services/authService.js`, `register`, allows callers to choose the administrator role without an existing administrator authorizing it. The public registration UI no longer offers that option, but direct requests still work. Restrict self-registration roles on the server and provide an authenticated administrator provisioning path before external deployment.

- **Order detail exposes the customer's full user record.** `server/src/services/orderService.js`, `getOrderById`, uses `customer: true`, which includes the stored password hash. The UI only renders the customer's name and email, but UI filtering cannot prevent API disclosure. Replace this relation with an explicit safe-field `select`, including only fields required by callers. Add a server regression test ensuring no password field is serialized.
- **Supplier order detail exposes other suppliers' lines.** The same `getOrderById` function verifies that at least one line belongs to a supplier, then returns the complete order. `updateOrderStatus` also returns every line. The supplier UI now displays only the supplier's own products and their subtotal. Enforce that projection in both server responses and verify it using a mixed-supplier order; frontend hiding is not an authorization boundary.
- **Order status transitions are not enforced.** `server/src/services/orderService.js`, `updateOrderStatus`, contains `TODO: enforce status transitions` and accepts the provided status. The UI permits `PENDING → PROCESSING/CANCELLED`, `PROCESSING → SHIPPED/CANCELLED`, and `SHIPPED → DELIVERED`; terminal orders cannot be reopened through this UI. Validate an allowlist and transition matrix on the server so direct API calls cannot bypass it. The server permits supplier updates to affect the entire order even when it includes another supplier's products. The UI now blocks those mixed-supplier updates and directs the user to an administrator; the server must model fulfillment per supplier or enforce the same restriction.
- **Concurrent orders can oversell.** `server/src/services/orderService.js`, `createOrder`, reads and validates stock before the write transaction and then decrements stock without a conditional availability check. Validate positive whole-number quantities server-side and reserve/decrement available stock atomically inside the transaction. The client validates quantities, but cannot guarantee consistency between concurrent buyers.
- **Concurrent stock adjustments can lose updates.** `server/src/services/stockService.js`, `adjustStock`, reads quantity before its transaction and writes an absolute value. Use an atomic increment with concurrency-safe nonnegative validation and a corresponding audit transaction. Also validate integer bounds and reason length on the server.
- **Product updates accept the request body directly.** `server/src/services/productService.js`, `updateProduct`, passes `data` into Prisma after an ownership check. The frontend sends only catalog fields, but the server should explicitly allowlist fields, validate every value and foreign-key ownership, and prevent suppliers from reassigning ownership through direct requests.

## Operational limitations

- **Backend dependencies still need review.** On October 15, 2026, `npm audit --workspace server` reported four findings (three moderate, one critical, including `proxy-addr`). Server dependency declarations were preserved under the backend scope restriction. The upgraded frontend dependency audit reports zero findings.

- **Cancelling an order does not restore stock.** `server/src/services/orderService.js`, `updateOrderStatus`, updates only the order status. The UI states this when selecting cancellation. Until inventory restoration is implemented transactionally and idempotently, returned units must be recorded through a manual stock adjustment.
- **The product update API can change quantity without an audit entry.** `server/src/services/productService.js`, `updateProduct`, does not write a stock transaction. The product edit UI now omits quantity entirely so an edit cannot overwrite newer inventory, shows the quantity observed when the form opened as read-only reference, and directs stock changes to the inventory adjustment workflow. A future backend change should prevent unaudited quantity updates through direct API calls or route them through the same transactional audit logic.
- **The products API's low-stock filter uses a single threshold.** `server/src/services/productService.js`, `getAll`, uses `filters.lowStockThreshold || 10` rather than each product's `lowStockThreshold`. The admin catalog therefore applies its low-stock filter locally to the returned products. Inventory exception views use the existing stock service, which compares each product's own threshold.
- **The admin dashboard API also counts low stock using 10.** `server/src/services/dashboardService.js`, `getAdminMetrics`, counts `quantity <= 10`. The admin dashboard UI uses the fetched low-stock exception list length so its card agrees with each product's actual reorder threshold and its exception queue.
- **Stock transaction listing is not implemented.** `server/src/controllers/stock.controller.js`, `getStockTransactionsController`, returns HTTP 501. The frontend shows an unavailable state; it does not invent an audit ledger or claim cryptographic immutability.
- **Customer discovery is partial.** There is no dedicated customer directory endpoint. The admin directory lists customers present on orders, while the registered customer metric comes from the dashboard. Registered customers without orders are not individually discoverable in that table.
- **Account administration is limited.** The profile API supports name and email. Password changes, MFA, role editing, supplier company editing, and session revocation are not exposed, so the UI does not present simulated controls.
- **Images are presentation metadata.** The current Product model has no image field. Free illustrative photographs are mapped by SKU in `client/src/data/product-images.json`; attribution appears on product details. Unmapped SKUs or failed image requests display an accessible placeholder. New product photographs require a manifest update until the backend supports media fields.
- **Tax, freight, and delivery tracking are not supported.** Cart totals contain product prices only. The UI displays real order fulfillment status and does not fabricate carrier locations, delivery dates, or tax charges.
- **AI forecasting is not implemented.** The existing AI routes return HTTP 501. AI panels must show availability honestly. Rule-based n8n notifications can run without paid AI; connecting an automation does not turn its stock rules into AI predictions.

## Frontend protections added

Catalog searches accept keyboard submission, no longer mistake click events for search text, and ignore stale overlapping responses. Stock forms require valid nonnegative whole-number quantities, safe prices and real selections; stock adjustment reasons are required. Cart quantities are checked before checkout. Order-detail failures stay inside their dialog, successful updates preserve dialog state, and terminal transitions are disabled. Failed dashboard requests show recovery controls instead of misleading empty metrics. Product imagery, form labels, live notices, responsive filters, pagination, and supplier line subtotals improve access and reviewability.

Client validation improves the interface but does not replace server validation or authorization. The findings above describe unresolved backend behavior, not a claim that the application has passed a production security assessment.
